# Word 文档制作技能

用 `scripts/build_doc.py` 从 JSON 大纲生成 .docx。**不要**自己用 python-docx 从零写排版代码——格式规范已固化在脚本里，绕过它就放弃了质量保障。

## 运行环境（先读）

技能内容末尾附有「运行环境」块，两种状态：

- **已就绪**：块里给出隔离环境的 Python 解释器绝对路径。下文所有 `python` 命令都换成这个路径执行。**禁止**使用系统 python3/python，**禁止**用 pip 往系统环境安装任何包。
- **未就绪**：调用 `skill_env_setup` 工具自动安装（Miniconda + 依赖，不改动用户系统 Python，首次约需 3-10 分钟），装完用工具返回的解释器路径继续。安装失败或被拒绝时，告知用户也可在「插件 → 技能详情」里手动安装。

## 工作流程

### 1. 确认文档类型与关键信息（必须先问，禁止猜测）

**用户没有明确说明文档类型时，必须先调用 AskUserQuestion 工具询问，等用户选择后再继续。不要根据上下文自行推断，不要用默认值直接开工。**

只有用户消息里已经明确写出（如「写一份请示公文」「整理成论文格式」「出个公司通知」）才可跳过类型提问。「帮我写个文档」「把这份内容整理成 Word」这类说法**不算**明确，必须问。

用 AskUserQuestion 询问**文档类型**：

- `official` 党政机关公文（通知、请示、报告、函；GB/T 9704-2012 红头格式，规范见 `references/official-format.md`）
- `thesis` 学术论文（摘要、关键词、自动章节编号、GB/T 7714 参考文献，规范见 `references/thesis-format.md`）
- `enterprise` 企业内部文档（公司通知、工作报告、方案、制度，规范见 `references/enterprise-format.md`）

类型明确后，写作前还须收集该类型的关键信息——**缺的才问，用户已给的不要重复问**：

- 公文：发文机关（是否红头）、发文字号、主送机关、落款单位、成文日期
- 论文：作者、单位
- 企业文档：单位抬头（可选）、落款与日期（可选）

### 2. 拟稿

- 内容归你：观点、逻辑、措辞精炼；格式归脚本
- 长文先把提纲（章节列表）给用户看一眼，确认后再生成，避免返工
- 公文注意文种与用语规范；论文摘要按「目的—方法—结果—结论」写

### 3. 写 JSON 大纲文件

按 `scripts/build_doc.py --schema` 输出的契约写 `<工作目录>/doc.json`。

- 公文/论文的章节编号由脚本自动完成（公文：一、（一）1.（1）；论文：1、1.1、1.1.1），**不要**手写编号
- 表格：列 ≤8、行 ≤50；图片用绝对路径
- 论文的图表标题（caption）必填，编号「图1/表1」由脚本自动完成

### 4. 生成

```bash
<运行环境块给出的 Python 解释器> scripts/build_doc.py doc.json
```

脚本会**校验并拒绝**违反格式规范的内容（日期格式、主送机关冒号、图表缺题注等），报错信息会告诉你怎么改；修正后重跑。生成成功输出 .docx 的绝对路径。

### 5. 视觉自检（有 LibreOffice 时必做）

```bash
<运行环境块给出的 Python 解释器> scripts/render_preview.py <产出.docx>
```

它把每页渲染成 PNG（依赖 soffice + pypdfium2）。用 read_media_file **逐页查看**，检查：

- 字体层级是否清晰（标题/正文/落款层次分明）
- 红头、红线、落款右对齐位置是否正常
- 表格是否跨页断裂、图片是否变形

发现问题 → 修改 doc.json → 重新生成 → 重新自检，最多迭代 2 轮。没有 soffice 时跳过并告知用户「未做视觉自检，建议打开文件检查排版」。

### 6. 交付

把 .docx 的完整路径告诉用户，附一句话说明（模板类型、页数估计、是否通过视觉自检）。

## 原则

- **内容归你，格式归脚本**。不要在 JSON 里传自定义字体/字号/颜色（脚本会拒绝）
- 公文红线：发文字号年份用六角括号〔〕；成文日期用阿拉伯数字（2026年3月5日，不编虚位）；层次标题不得越级
- 论文参考文献条目由你按 GB/T 7714 著录（作者. 题名[J]. 刊名, 年, 卷(期): 页码.），脚本只排版不代写
- 用户提供的素材优先用进正文，不要编造数据
